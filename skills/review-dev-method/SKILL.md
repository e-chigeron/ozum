# 開発手法を見直す

ОЗУМでこの手順が実現する目的は [method-evolution](../../Intent/method-evolution.md) と [instruction-ownership](../../Intent/instruction-ownership.md)。配布先では、そのプロジェクトが指定する関連Intentを参照する。これらのОЗУМへの参照は配布先の実行依存ではない。

摩擦は、開発の進行・判断・品質を妨げる観測された支障や負担を指す。例えば「仕様の所在を探して同じ文書を何度も読んだ」は観測、「入口が不明瞭」は原因仮説、「参照を追加する」は改善案であり、分けて扱う。一度の製品バグを手法全体の欠陥と決めつけない。明示的な手法レビューでは、過去の失敗がなくても改善仮説を検討できる。

摩擦の発生条件、頻度、影響、現在の回避策を、確認できる証拠とともに整理する。未確認の仮説は観測事実と分ける。

開発プロジェクトから改善候補を上流へ渡す場合は、証拠をそのプロジェクトに保ち、証拠の参照、一般化できる範囲、候補変更、成功条件と取消条件を添える。上流の編集まで依頼されていなければ、別リポジトリの手法を直接変更しない。転送形式は指定せず、元の会話全文も要求しない。

観測の記録だけなら改善提案の作成は不要。上流へ提案する場合は、ОЗУМのメタ開発手法、ОЗУМリポジトリのリファレンス実装、開発手法テンプレート、Skillsのどれを変えるかを明示する。テンプレートやSkillsの変更を、リファレンス実装の変更として扱わない。

上流では `Intent/` と `AGENTS.md`、関係するFeature Spec・Skills・雛形を確認する。ОЗУМの保守方法のFeature Specは `AGENTS.md`、特定作業の契約は各 `SKILL.md` に直接表現され、目的への参照もそこから辿れる。現在の方法で扱えない理由を検討し、必要な箇所だけGit履歴で以前の判断を調べる。

指示や仕組みの追加だけでなく、変更・削除も含めて最小の改善を選ぶ。常時contextと保守負担、既存機能との重複、外部への接続・乗換えの負担、成功条件と取消条件を示す。採用した方法・契約はFeature Specへ、目的・制約も変わる場合だけIntentへ反映し、変更理由は日本語のコミットメッセージへ残す。実装は依頼された範囲で行い、commitとpushは適用先のプロジェクト指示に従う。

用語・書式を改善するときは、定義と判断例の明確化を先に検討する。YAML front matterを全体へ必須化せず、必要なら現行文書、説明を改善した文書、さらにメタデータを付けた文書を同じ代表課題で比較する。読む対象・変更対象・無断の仕様変更・不要な質問や成果物を評価し、効果がある範囲だけ採用する。構文やリンクの検査は意味の正しさを保証しない。本文とメタデータの二重管理を避け、既存Skill形式の互換性を保つ。
